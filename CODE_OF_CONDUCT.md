# Code of Conduct

RoasterBro roasts codebases, not people. Keep that distinction intact everywhere in this project — issues, PRs, discussions, commit messages, code review comments, all of it.

## The short version

Don't be a jerk to other contributors. Disagree about code as much as you want; don't make it personal.

## What's fine

- Blunt, technical criticism. "This regex will silently swallow malformed TOML, here's why" is exactly the kind of feedback this project wants, said as directly as you like.
- Pushing back on a design decision, including the maintainer's.
- Closing/rejecting a PR with a clear technical reason.
- Disagreeing in the issue tracker until it's resolved.

## What's not fine

- Attacking a person instead of their code. "This function has a bug" is fine. "You clearly don't know what you're doing" is not.
- Sarcasm or mockery aimed at a contributor's skill level, background, identity, or the fact that they're new to open source. (Yes, this project's own product roasts *code* — that's a deliberate, opt-in feature aimed at a repo's engineering habits, not a license for maintainers or contributors to roast each other.)
- Harassment, in any form — repeated unwanted contact, discriminatory jokes, sexualized comments, doxxing, threats.
- Deliberately derailing issues/PRs with off-topic arguments.
- Impersonating another contributor or maintainer.
- Submitting a PR just to pick a fight in review, or review comments written to embarrass rather than to improve the code.

## Scope

This applies anywhere the project happens: GitHub issues, PRs, discussions, and any other space explicitly tied to RoasterBro (e.g. a project Discord/Slack, if one exists in the future). It also applies if you're representing the project elsewhere (e.g. tweeting as "a RoasterBro maintainer").

For security vulnerabilities specifically (as opposed to conduct issues), use [SECURITY.md](SECURITY.md) instead — don't file those as conduct reports.

## Enforcement

This is a small, early-stage project maintained mostly by one person, so there's no formal committee — enforcement is maintainer judgment, applied consistently and proportionally:

1. **First instance, minor:** a direct, private heads-up. Most things stop here.
2. **Repeated or more serious:** a warning on the issue/PR itself, and the offending content may be edited or removed.
3. **Continued or severe (harassment, threats, doxxing):** the contributor is blocked from the project's spaces. No extended appeals process for clear-cut cases — this exists to protect contributors, not to be maximally lenient toward bad actors.

Maintainers are held to the same standard, not a looser one.

## Why this exists

Not because this project expects trouble — it's because "roast your codebase" is baked into the product's identity, and it's worth being explicit, once, that the joke is about `git blame` output, dependency choices, and missing tests, never about the person who wrote them.
